### 1. Проблема Horizon Truncation у великих каталогах

Коли користувач ставить неповний або розмовний запит (*«відеокарта сорок шістдесят від гігабайт»*, *«літнє плаття zara»*), традиційні Text-to-SQL системи зазнають **Horizon Truncation** (обрізання горизонту пошуку):

```
КАТАЛОГ НА 100 000 ТОВАРІВ
┌────────────────────────────────────────────────────────────────────────┐
│  Запит LLM: SELECT * FROM products WHERE brand = 'Gigabyte' LIMIT 20;  │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
       Повертаються перші 20 карток (наприклад, старі GT 710 або кулери)
                                    │
                                    ▼
       RTX 4060 опиняється на 142-му місці (ПОЗА ГОРИЗОНТОМ LIMIT 20)
                                    │
                                    ▼
  Вердикт моделі: «У нас немає RTX 4060, є тільки застарілі відеокарти» (Помилка!)
```

Причини проблеми:
1. **Плаский пошук (Flat Search):** база сприймається як суцільний масив рядків без ієрархічної глибини;
2. **Лінгвістична неоднозначність:** розмовна форма числівників (*«сорок шістдесят»*) не збігається посимвольно з маркуванням виробника (*«RTX 4060»*);
3. **Обмеження контексту LLM:** передати 1000 карток у промпт неможливо через затримку та вичерпання вікна контексту.

### 2. Математичний апарат: Formal Concept Analysis (FCA)

Для вирішення цієї проблеми система реалізує **Formal Concept Analysis (Аналіз формальних понять)** — розділ прикладної абстрактної алгебри, що будує ґратку понять на основі бінарного контексту.

#### Формальний контекст $(G, M, I)$:
* $G$ (Gegenstände / Objects) — множина товарів у каталозі ($g \in G$);
* $M$ (Merkmale / Attributes) — множина фасетних властивостей ($m \in M$): категорія, бренд, тип, дискретні параметри;
* $I \subseteq G \times M$ — відношення інцидентності: $(g, m) \in I$ означає «товар $g$ має властивість $m$».

#### Оператори замикання Галуа (Galois Derivation Operators):
Для множини товарів $A \subseteq G$ та множини атрибутів $B \subseteq M$:
$$A' = \{ m \in M \mid \forall g \in A: (g, m) \in I \}$$
$$B' = \{ g \in G \mid \forall m \in B: (g, m) \in I \}$$

#### Формальне поняття (Formal Concept):
Пара $(A, B)$ називається **формальним поняттям**, якщо:
$$A' = B \quad \text{та} \quad B' = A$$
* $A = \text{Extent}$ (Обсяг поняття) — множина всіх товарів, які підпадають під цей клас.
* $B = \text{Intent}$ (Зміст поняття) — повний набір спільних властивостей, якими володіють ці товари.

#### Ґратка понять (Concept Lattice):
Поняття впорядковані відношенням підпоняття / надпоняття:
$$(A_1, B_1) \le (A_2, B_2) \iff A_1 \subseteq A_2 \ (\iff B_2 \subseteq B_1)$$
Ця структура утворює повну ґратку (Complete Lattice) з найвищим поняттям $\text{TOP}$ (усі товари, порожній зміст) та найнижчим $\text{BOTTOM}$.

### 3. Архітектура рушія `FCATaxonomyEngine`

Файл: [`src/core/taxonomy_fca.py`](../../src/core/taxonomy_fca.py)

Під час підключення бази даних рушій будує ієрархічну ґратку понять за 3 кроки:

```mermaid
graph TD
    subgraph FCALatticeStructure ["Ієрархічна ґратка понять каталогу L(G, M, I)"]
        Root["Рівень 0: Root (Всі товари)"]
        
        Root --> CatClothing["Рівень 1: Категорія 'Одяг'"]
        Root --> CatGPU["Рівень 1: Категорія 'Відеокарти GPU'"]
        Root --> CatAuto["Рівень 1: Категорія 'Автотовари'"]
        
        CatGPU --> ConceptGigabyte["Рівень 2: Поняття (category:gpu, brand:Gigabyte)"]
        CatGPU --> ConceptASUS["Рівень 2: Поняття (category:gpu, brand:ASUS)"]
        
        ConceptGigabyte --> Leaf4060["Рівень 3: Товари (RTX 4060 Windforce Rev 1-4)"]
        ConceptGigabyte --> Leaf4070["Рівень 3: Товари (RTX 4070 Eagle)"]
    end
    
    Query[Запит клієнта: 'Gigabyte 4060 GPU'] --> Engine[FCATaxonomyEngine.navigate]
    Engine --> Match[Intent Coverage Scoring: O(log N)]
    Match --> TargetConcept[Точна локалізація: ConceptGigabyte]
    TargetConcept --> SampleIDs[Вибірка sample_ids: пряме попадання без сліпого LIMIT]
```

1. **Рівень 0 (Supremum):**
   - Корінь каталогу: охоплює 100% об'єктів ($|A| = N$), зміст $B = \emptyset$.
2. **Рівень 1 (Макро-категорії):**
   - Поняття з інтентом `{category: X}` (наприклад: `gpu`, `motherboard`, `women_clothing`, `auto_tires`).
3. **Рівень 2 (Підкатегорії та вендорні кластери):**
   - Специфічніші поняття з інтентом `{category: X, brand: Y}`. Обсяг звужується від тисяч товарів до десятків конкретних позицій.
4. **Рівень 3 (Фасетні параметри):**
   - Специфікації конкретних моделей (сокет, обсяг VRAM, розмір, колір).

### 4. Алгоритм навігації та Intent Coverage Scoring

Метод `navigate(query)`:
1. Запит розбивається на токени з урахуванням меж слів (Word Boundary Detection), що запобігає хибним збігам (наприклад, слово `men_clothing` не матчиться всередині `women_clothing`).
2. Для кожного поняття обчислюється коефіцієнт покриття інтенту (Intent Coverage Ratio):
   $$\text{Coverage}(C) = \frac{|\{ m \in \text{Intent}(C) \mid m \text{ присутній у запиті} \}|}{|\text{Intent}(C)|}$$
3. Поняття з повним покриттям ($\text{Coverage} = 1.0$) та максимальною глибиною (level) обирається як цільове.
4. Система миттєво повертає:
   - `concept_id` — точний вузол ґратки;
   - `extent_size` — реальну кількість товарів у цій підгрупі;
   - `sample_ids` — конкретні ID товарів для гарантованого заземлення;
   - `available_subcategories` — доступні гілки для подальшого уточнення.
